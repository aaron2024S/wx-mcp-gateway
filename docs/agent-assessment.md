# 网关作为一个 agent 的能力评估

- 评估时间：2026-11-12
- 代码基线：`a78c481`（HEAD，CLI 连接器已接入，未发版）
- 结论一句话：**是 agent 的运行时，但只跑得动「一句话能说完的一件事」。**

---

## 一、结论

**算，但只能算窄口径 agent。**

它与 WorkBuddy 那类 agent 处在同一个范式里（模型决定动作 → 观察结果 → 继续决策），
但它是**反应式、单会话、无记忆、单任务**的。对标的是 Codebuddy 的「单轮任务模式」，
不是它的自主模式。

判定不靠感觉，靠一条：**下一步做什么，是模型看过上一步结果之后决定的，还是代码里 if/else 写死的。**
这一条它满足——`routeWithLLM`（单轮路由）还在，但只被「测试服务商连接」这个接口用着，
业务链路已经没有它了。

---

## 二、控制流（实际实现，不是设计稿）

```
微信一句话
   │
   ├─→ 模型看「应用目录」（每应用一行，schema 不进上下文）
   │      │
   │      └─→ search_tools(自己决定的检索词)  ←── 检索器只排序，不做决定
   │             └─→ 命中工具的 schema 挂进本轮上下文
   │
   ├─→ 调一个工具 ──→ 读操作：自动执行
   │                    └─→ 结果回灌（模型看带 uid 的版本，用户看不带）
   │                 └─→ 写/高危：halt，交给确认流程，**闭环到此结束**
   │
   ├─→ 回到上一步，最多 6 轮 / 45 秒
   │
   └─→ 模型不再调工具 → 给出回答（3-6 句中文）
```

四个刹车（都在 `llm.js` 里，全部返回结构化 `stop` 值，不抛异常）：

| 刹车 | 行为 | 位置 |
|---|---|---|
| `max-rounds` | 轮数用完，把已查到的先发出去 | `llm.js:654` |
| `timeout` | 超时间预算，说「花的时间太长」 | `llm.js:579` |
| `no-progress` | 同工具同参数连续两次，判定原地打转 | `llm.js:638` |
| `halt` | 碰到写操作，转人工确认后**不再回到循环** | `llm.js:628` |

## 三、已经具备的（这就是它能叫 agent 的原因）

| 要素 | 实现 | 说明 |
|---|---|---|
| 模型决定下一步 | `llm.js:542` `agentLoop` | 检索词、工具选择、是否继续，全由模型发起 |
| 观察→再决策 | 结果以 `role:tool` 回灌 | 允许换词重试，最多两次（提示词第 5 条） |
| 多步推进 | 单轮 6 次工具调用 / 45 秒 | e2e ④m 钉的就是「检索→搜邮件→读正文→摘要」四步 |
| 工具发现 | 目录 ~700 token + `search_tools` | 22 个工具全量 schema 是 4.5k token；工具不砍也不炸上下文 |
| 统一工具层 | `registry.search` + MCP/CLI 同契约 | 上层不知道底下是 HTTP 还是子进程 |
| 权限边界 | `allow_risk` 硬上限 + `confirm_risk` + TTL | 读自动、写必确认，比多数 agent 严 |
| 会话状态 | `session.js:25` | 确认 / 候选 / 补参 / 序号引用，四种待决互斥 |
| 可观测 | trace + token + 调用日志 + 自检 | 「贴一句话试试」跑同一条闭环，把执行换成「到此为止」 |
| 失败降级 | 结果压缩、超时先发、编造工具名被丢 | 模型看不到 8k 正文，压到 2000 字（`agent.js:425`） |

## 四、明确不具备的（不是没写完，是结构性的）

### 1. 没有长期记忆

`SessionStore` 是纯内存 `Map`（`session.js:25`），容器重启即清空；
对话历史只留 **3 轮**、每轮结果截 700 字（`session.js:17`、`agent.js:776`）。

> 影响：它不记得「NAS 叫网盘」「上次查的是 2019 年的邮件」「用户讨厌分点列表」。
> 每次对话都是第一次见你。这是它和「越用越顺手」之间最大的那道墙。

### 2. 没有主动性

只能被入站消息唤醒。`"帮我盯着，磁盘超 80% 就告诉我"` 做不到。

> 影响：它是个遥控器，不是助手。微信入口本来最该做「主动推一条」，现在这条能力空着。

### 3. 一轮只调一个工具

提示词第 2 条（`llm.js:441`）明写「每一轮只调一个工具」，adapter 也只取 `tool_calls[0]`。

> 影响：「查这三个应用的状态」要三次往返 —— 三次往返 = 三次 token + 三轮延迟。
> 并行调用能把这部分成本直接砍到 1/3。

### 4. 写操作确认后闭环断开

`_loopExec` 遇到 `risk !== 'read'` 直接 `halt`（`agent.js:425`），
确认后走 `_run` 执行一条、渲染结果、回话，**不会回到循环继续规划**。

> 影响：「删掉它，然后告诉我邮箱还剩几封」—— 删完就结束了，不会再去数。
> 这是刻意的安全取舍（确认过的动作不能顺手带出第二个动作），但它确实把多步写任务切断了。

### 5. 没有计划、子 agent、自己的执行环境

不能写文件、不能跑自己的脚本、没有 todo list、没有任务分解。
它唯一的执行力来自接进来的工具（MCP 工具 / CLI 子命令）。

## 五、和 WorkBuddy 的真实差距

**不是工具接入。** 这块已经对齐了：MCP + CLI 统一契约、目录 + 按需检索、
风险分级、二次确认、审计日志 —— WorkBuddy「挂几百个连接器不慢」的那套机制，
这个网关已经有了，而且检索器是中文分词 + idf，比关键词搜索更准。

**差距在两层，而且都不在工具侧：**

1. **记忆**（跨会话的稳定事实 + 工作日志）
2. **主动性**（定时 / 条件触发 → 主动推送）

## 六、如果要继续走，优先级

| 优先级 | 做什么 | 大致成本 | 收益 |
|---|---|---|---|
| P0 | 记忆落盘：`data/MEMORY.md`（稳定事实）+ 最近 N 天日志摘要，拼进系统提示词 | ~100 行，1 天 | 从「每次都是第一次」变成「认识你」 |
| P1 | 并行工具调用：adapter 取全部 `tool_calls`、放开提示词第 2 条 | 半天 | 多查询任务成本降到 1/3 |
| P2 | 主动触发：cron + 条件（磁盘水位、新邮件、容器退出）→ 主动推一条 | 2-3 天 | 从遥控器变成助手 |
| P3 | 计划列表：多步任务的可视化与断点续跑 | 3 天+ | 复杂任务可用，但收益取决于有没有 P0/P2 |
| — | 确认后继续闭环（缺口 4） | 1 天 | 需重新设计安全边界，**不建议顺手做** |

---

## 七、刻意不做的事（写下来，免得以后被自己重新捡起来）

1. **代码执行沙箱。** 为了「远程操作台」去开一个能跑任意代码的口子，风险和收益完全不成比例。
2. **本地匹配兜底。** 已删除。本地预筛是一种**不可恢复的过滤**——未命中的那句话在模型看见之前就被扔了。
   检索器只排序、不做决定，最坏情况是排得靠后，而不是永远搜不到。
3. **每轮工具都全量进上下文。** 会把 4.5k token 变成常驻 20k，且每轮重复计费。
4. **让模型直接决定「要不要执行写操作」。** 风险判断必须在执行层，模型碰不到。
